# Test runs — 2026-11-23

Runs of 2026-11-23. Not cases of [the test plan](../../README.md#test-plan--the-real-device-pass-step-6e):
a control for the [2026-11-22 run](2026-11-22.md), which read the carrier's NAT from the source ports
of a phone's requests. Part of the record in [README.md](README.md): append-only.

Why it was needed: that method reads the NAT only if the browser asks both servers from one socket,
and its control was Chrome. The owner named the phones the next day — iPhones, Safari — and Safari in
the iOS Simulator turned out to send every STUN request from a port of its own.

All four measurements ran on the home line (Epic, the Mac's Wi-Fi), against
`stun.hushsend.frelikh.dev:3479`, `turn.hushsend.frelikh.dev:3478` (asked as a STUN server) and
`stun.l.google.com:19302`.

## The home NAT — endpoint-independent, port kept

One UDP socket in node on the Mac, a Binding request to each of the three servers and to
`stun.cloudflare.com:3478`: local port 58926, and every server answered with the same public address
and port 58926. So on this line a `srflx` port IS the local port the request left from.

## How many sockets a browser uses for three STUN servers

One `RTCPeerConnection` with the three servers and a data channel, candidates read from
`icecandidate`; three connections per browser.

| Browser | `host` port | `srflx` | Runs |
|---|---|---|---|
| Safari 26.5.2, macOS 26.5.2 (the live page, script injected) | 58186 · 60050 · 61279 | one, the same port as `host` | 3 of 3 |
| Safari 26.5, iOS Simulator (iPhone 17e), a page served from the Mac | 51340 · 60435 · 65241 | three, three different ports, none of them the `host` port (49846 / 54093 / 54492 in the first) | 3 of 3 |
| Safari 27.2 on an iPhone, home Wi-Fi, the same page | 56828 · 58103 · 63993 | one, the same port as `host` | 3 of 3 |

- Safari on a real iPhone and on macOS asks all three servers from one socket, like Chrome.
- Safari in the iOS Simulator does not: each server is asked from its own local port. On any network
  it looks like a host behind a symmetric NAT, so a simulator run says nothing about a NAT.
- The iPhone's model was not recorded; the page was reachable from the home network only.

## What this does to the 2026-11-22 verdict

It stands: the phones' two source ports were two mappings of one socket, so Epic's mobile NAT is
symmetric. What was not repeated on an iPhone is the TURN half of that method — that the request to
3478 in Reliable leaves from the same socket as the STUN one. It does in Chrome (the 2026-11-22
control), and here an iPhone asked `:3478` as a STUN server from that socket.

## Two fingerprint lines in a description — what each engine does

For the [one-fingerprint rule](../../README.md#crypto). Playwright 1.65 builds on the Mac: Chromium
158.0.8127.18, Firefox 159.0, WebKit 27.2. Not measured: Safari itself (macOS, iOS), Firefox on
Android.

Method: one page, two `RTCPeerConnection`s and a data channel; the OFFER is edited before
`setRemoteDescription` on the answering side, the answer is passed through. "Another" is a random
SHA-256 fingerprint, "honest" the offerer's own. Read back: the fingerprint lines the engine keeps in
`remoteDescription.sdp`, the first of them (what the code read until this day), and whether the
channel opened within 8 s. One run per engine and arrangement.

| The offer carries | Chromium 158 | WebKit 27.2 | Firefox 159 |
|---|---|---|---|
| the honest line only | opens · first line = honest | the same | the same |
| another, then the honest one, at one level | opens · keeps only the honest one | the same | **opens · keeps both · first line = the other** |
| the honest one, then another, at one level | fails · keeps only the other | the same | **opens · keeps both · first line = honest** |
| another at session level, the honest one at media level | opens · keeps only the honest one | the same | **opens · keeps both · first line = the other** |
| the honest one at session level, another at media level | fails · keeps only the other | the same | fails · keeps both · first line = honest |
| another only | fails | fails | fails |

- **Chromium and WebKit** take one line — the last at the level in force, media over session — check
  the certificate against it and serialize only that line back. The first line of the text is always
  the certificate that was checked.
- **Firefox** checks the certificate against every line at the level in force (media-level lines
  replace session-level ones) and serializes back all it was given. In the third row the certificate
  that matched is NOT the only one that could have: a peer holding the other certificate would have
  been accepted, and the code would still have read the honest fingerprint.
- **`getRemoteCertificates()`** on the connection's DTLS transport, after the channel opened: one
  certificate, and its SHA-256 equal to the fingerprint of the description, in all three engines.

**The app before the fix** (`0fdd853`), two tabs of one engine, one tab adding a second line to every
description it sends (`tests/e2e/fingerprint.spec.ts`, which the fixed app passes 12 of 12):

| What the other tab received | Chromium | Firefox |
|---|---|---|
| link · honest, then another | "Couldn't connect directly" (DTLS against the other) | **connected** |
| link · another, then honest | connected (the other line dropped by the engine) | channel opened, then key-confirmation mismatch |
| link · another at session level | connected (the same) | channel opened, then key-confirmation mismatch |
| room · honest, then another | "Couldn't connect directly" | **the three words shown on both sides** |

WebKit stayed on "Agreeing on keys…" in all four: that run had no loopback STUN server, without
which Playwright's WebKit connects nothing here, so it says nothing either way.

**Not carried out: the interposition itself.** What is measured is that a Firefox pair accepts a
description naming a second certificate and authenticates over the first — the two things a server
in the middle needs on each side. A server holding that second certificate and terminating both DTLS
legs was not built.
