## 2026-10-11 · STUN probe from the server's own LAN (laptop-server, 192.168.1.19, Wi-Fi) — what the home side advertises

Run with Claude in the session that recorded the entry above. One UDP socket (local port 55497), a STUN
binding request to four destinations, the mapped address read from XOR-MAPPED-ADDRESS:

| Destination | Mapped address |
|---|---|
| `stun.hushsend.frelikh.dev:3479` (the live bundle's STUN, `hushsend-stun.service`) | `94.46.199.61:55497` |
| `stun.hushsend.frelikh.dev:3478` (the TURN relay, `coturn.service` — what 2026-10-03 measured) | `192.168.1.1:55497` |
| `stun.cloudflare.com:3478` | `94.46.199.61:55497` |
| `stun.l.google.com:19302` | `94.46.199.61:55497` |

- The home router gives the public IP with the local port preserved and the SAME mapping for every
  destination (endpoint-independent mapping — a cone NAT, the easy kind). Through the live bundle's
  `:3479` a laptop on this Wi-Fi advertises a reachable `srflx`; the 2026-10-03 "failure by
  construction" applied to `:3478` and is gone from the live bundle.
- `turnutils_stunclient -p 3479` from the same host agrees (`94.46.199.61`).
- Unexplained: both coturn templates set `external-ip`, yet only the `:3478` listener reports the
  router's LAN address for a hairpinned request.
- Not measured: the router's FILTERING (needs an outside host sending unsolicited UDP to the mapped
  port) and anything about the phone's carrier NAT. No IPv6 on the LAN (`ip -6 addr`: no global
  address) and no AAAA for the STUN host, so an IPv4 NAT traversal is the only direct path available.
- What this changes: the failure above is NOT explained by the stand any more. The remaining
  explanations are a symmetric carrier NAT on the phone (common on mobile CGNAT; STUN alone cannot
  traverse it unless the far side filters by address at most) or port-restricted filtering at home.
  BACKLOG § Pre-launch review carries the next step: capture the candidate pairs of such a pair.

## 2026-10-11 · Claude, the Mac's built-in Chromium, two tabs · a joiner whose browser has no WebRTC

Not a TESTPLAN case: what a person sees in a browser with WebRTC switched off (some privacy browsers
and hardened Firefox configurations do that; which ones exactly was not checked), asked before
deciding on an up-front check. Live bundle
`index-BxZIampM.js`, link method, Max privacy. Tab A created a link; tab B loaded the home page, had
`window.RTCPeerConnection` deleted, and was given the link as its fragment (the `hashchange` join).

- Tab B joined, then threw `Uncaught (in promise) ReferenceError: RTCPeerConnection is not defined`
  from `startPeer` — unhandled, nothing reached the screen.
- **Both tabs sat on "Agreeing on keys…" for about 165 s** with no change, then failed together when the
  server's token-room TTL (180 s from the link's creation) closed the sockets with 4010: both read
  **"Room not found or code expired — Check the digits or start your own room"**, the joiner's copy for
  a mistyped 4-digit code, on a link pairing where no digits exist.
- What it shows beyond the missing check: between the start of pairing and an open DataChannel the
  link / QR / words methods have no client-side deadline — the 120 s confirmation deadline arms only
  once the channel is open (`runKeyConfirmation`). A peer that never answers the offer leaves the other
  side waiting for the untrusted server to expire the room. BACKLOG § Pre-launch review.
