# Test runs — 2026-11-22

Runs of 2026-11-22, in the order they ran. Not cases of [the test plan](../../README.md#test-plan--the-real-device-pass-step-6e):
a day spent on why Max privacy does not connect across networks. Part of the record in
[README.md](README.md): append-only — a later run that changes a verdict gets its own entry.

The owner's networks that day: two phones on the cellular network of Epic (Cyprus, AS15805) and a home
line of the same operator (the Mac on its Wi-Fi). Phone models and browsers were not recorded. The live
bundle was the 2026-11-07 app code (`26e52ad`); STUN `stun:stun.hushsend.frelikh.dev:3479`.

## STUN over IPv6 — enabled, and not used by these networks

The STUN server got an AAAA record and a listener on `::` that morning (hushsend-stun-server). Checked
on the host only (its global IPv6 address answers STUN and refuses an anonymous Allocate); from outside
it could not be asked — no network with IPv6 was at hand, and the firewall counter for `3479/udp` over
IPv6 stayed at 0 through every run below. Epic gives its subscribers no IPv6: APNIC's per-AS figure
for AS15805 was 0.47 % IPv6-capable that day (Cyta, AS6866: 44 %).

## Max ↔ Max across networks — two attempts, neither connected

- **A phone on Epic cellular ↔ a phone on Epic cellular** — did not connect. The STUN host saw four
  new IPv4 flows and none over IPv6.
- **The Mac on the home Wi-Fi ↔ a phone on Epic cellular** — did not connect. A packet capture on the
  STUN host (source address, source port, destination port of what reached 3478 / 3479; kept in RAM,
  deleted afterwards) showed both devices reaching STUN over IPv4, twice each.

## What the carrier's NAT does — measured

Method: in Reliable mode a browser asks STUN (3479) and TURN (3478) from ONE local socket, so the
source ports the server sees for the two requests are the NAT's mappings of that socket toward two
destinations.

| Device, network | source port → 3479 | source port → 3478 |
|---|---|---|
| phone A, Epic cellular | 27492 | 27493 |
| phone B, Epic cellular | 19629 | 19627 |
| a PC on the home line | 58131 | 58131 |
| Chrome on the Mac, home Wi-Fi (control) | 62936 | 62936 |

- The home router keeps one mapping for both destinations (endpoint-independent, as measured
  2026-10-11); the control shows the method reads the NAT, not the browser.
- Epic's mobile NAT hands out a NEW port per destination (a symmetric NAT), and the ports of mappings
  made at the same moment are neighbours. The base moves between attempts (phone A: 42327 in the run
  above).
- So a peer is told one port by STUN and is then reached from another: Max privacy cannot connect a
  phone on this network to another such phone or to a host behind an ordinary home router.

## Port prediction — works once, not adopted

A prototype outside the product: in Chrome on the Mac `RTCPeerConnection.prototype.addIceCandidate` was
patched on the live page to add, next to the peer's `srflx` candidate, the same address with ports −6 …
+24. Mac on the home Wi-Fi ↔ a phone on Epic cellular, Max ↔ Max, QR: connected on the first attempt,
about 0.2 s after the phone's candidate arrived — the phone announced port 42512 and the selected pair
used 42515. The app showed "Secure channel open", "direct path confirmed". One attempt; phone ↔ phone
was not tried (both sides would need it). The owner decided not to build it: it depends on how one
carrier numbers its ports ([Decisions](../../README.md#decisions)).
